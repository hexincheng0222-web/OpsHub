# OpsHub 用户体验评审报告

> 审查日期：2026-07-06
> 审查范围：整体导航体验 / 前端交互可用性 / 后端稳定性与安全（用户可感知）
> 审查视角：普通终端用户

本报告从用户视角出发，对 OpsHub 项目的可用性、交互一致性与稳定性进行审查。问题按严重程度分为 **严重（P0）/ 中等（P1）/ 轻度（P2）** 三档，每条均附有代码证据与改进建议。

---

## 1. 严重问题（P0 — 阻断体验 / 数据损失 / 安全）

### 1.1 离开首页后无跨模块导航，用户被困在单页面

**影响**：进入 `/services`、`/phones` 等子页面后，页面上不存在通往其他模块的路径，用户唯一的出路是返回首页重新点卡，跨模块操作成本极高。

**证据**：`src/App.vue:1–3` 整个文件只有 `<router-view />`，没有任何侧边栏、顶部导航或面包屑。Admin 模块（`src/views/admin/AdminView.vue`）内嵌了自己的侧边栏，但与主站业务模块风格割裂。

**建议**：

- 抽取全局布局（侧边栏 + 顶栏），把首页卡片中的 6 大模块（服务 / 手册 / 设备 / 采购 / 打印机 / 日志监控）作为一级菜单；
- 或至少在每个子页面顶部加面包屑 + 全局顶栏 Logo 链接。

---

### 1.2 登录成功忽视 `?redirect`，硬编码跳首页

**影响**：用户从 `/services` 被踢到 `/login?redirect=/services`，登录成功后却落在首页，需要再手动点一次卡片才能回到目标模块。属于明确 Bug。

**证据**：路由守卫在鉴权失败时**正确保存**了目标路径（`src/router/index.ts:148`），但登录 composable **完全无视**它（`src/composables/useLoginForm.ts:68`）：

```ts
// 当前实现
router.push('/')

// 建议修复
router.push((route.query.redirect as string) || '/')
```

**同类问题**：`token` 过期由 `src/utils/http.ts:36–46` 调用 `logout()`，跳转也未带 `redirect`，与守卫"保留来源路径"的设计不一致，建议补上 `?redirect=${encodeURIComponent(location.pathname)}`。

---

### 1.3 10 分钟无操作静默登出，编辑中内容丢失

**影响**：在 `ManDocEditor` 填长手册、或在任意表单填写超过 10 分钟未操作鼠标 / 键盘，会被直接踢到登录页，输入内容全部丢失。

**证据**：`src/App.vue:22–46` 的 `startIdleTimer` 在 `logout` 时仅调用 `router.push('/login')`，无任何"即将登出"提示，也无任何草稿暂存机制。

**建议**：

1. 停留即将到期前 60 秒弹倒计时确认框，提供"保持登录"按钮重置计时；
2. 编辑类页面在 `beforeunload` 或 `logout` 前用 `ElMessageBox.confirm` 兜底；
3. 计时器延到 30 分钟，并提供"记住我"持久化选项；
4. 长文本编辑器增加草稿自动保存到 `localStorage`。

---

### 1.4 三处表单保存按钮无 loading，可重复提交

**影响**：网络慢时用户连点，即可重复创建设备、打印机或手册条目。

**证据**：

- `src/components/devices/DeviceForm.vue:76`
- `src/views/PrintersView.vue:165`
- `src/views/ManDocEditor.vue:13`

三处按钮均无 `:loading` / `:disabled`，事件处理函数也无 `submitting` 状态守卫。

**建议**：每个表单页增加 `submitting` ref，入口处 `if (submitting.value) return`，按钮 `:disabled="submitting"` 或 `:loading="submitting"`。

---

### 1.5 token 过期处理路径混乱，可能重复请求与重复跳转

**影响**：`App.vue` onMounted、`router.beforeEach`、以及任一接口 401 回调这三处都会触发 `fetchMe` / `logout`，状态竞争下可能出现多次 `router.push('/login')`，前端也会因多个并行 401 而发送重复请求。

**证据**：

- `src/App.vue:52–54` onMounted 中 `fetchMe` 失败抛错后仍会执行下一行 `if (auth.isLoggedIn) resetTimer()`；
- `src/router/index.ts:137–139` 再次触发 `fetchMe`；
- `src/utils/http.ts:40` 调用 `logout`。

**建议**：收敛到单一 guard（推荐放在 `router.beforeEach`），401 跳转统一带 `redirect`，并做互斥锁防止并发登出。

---

### 1.6 字典 / 接口加载失败静默吞错，用户面对空白下拉

**影响**：设备型号、服务主机等下拉无数据时，用户无法判断是"真的没数据"还是"接口挂了"，直接卡死工作流。

**证据**：

- `src/components/devices/DeviceForm.vue:30` 仅 `console.error('加载字典数据失败:', e)`；
- `src/views/ServicesView.vue:186–187` 仅 `console.warn('加载主机列表失败:', e.message)`。

**建议**：至少调用 `ElMessage.warning('设备型号字典加载失败，请刷新重试')`，并提供重试按钮。

---

### 1.7 危险操作确认文案不一致，部分无后果说明

**影响**：用户不清楚操作后果，且跨页面心智负担高。

**证据**：各页面删除按钮标题与组件各异 —— `AdminUsers.vue:242` 用 `ElMessageBox.confirm`、`AdminServices.vue:39` 用 `el-popconfirm`、文案混用"删除 / 确认重置 / 清空 / 确认删除 / 删除确认"。

**建议**：

- 统一使用 `ElMessageBox.confirm`；
- 标题写明后果（如"删除后不可恢复，所有设备将被移除"）；
- 危险按钮统一命名为"删除"。

## 2. 中等问题（P1 — 明显痛点）

### 2.1 搜索 / 筛选状态未写入 URL，刷新即丢

**影响**：用户筛选后刷新页面条件全丢，也无法与他人分享带筛选的链接。

**证据**：`DevicesView.vue:40-46`、`PhonesView.vue:158`、`PhonebookView.vue:121-124`、`PrintersView.vue:236`、`ServicesView.vue:195-197` 等页面全部使用 `ref` 本地状态，无 `useRoute` / `router.push` 同步。仅 `ProcurementView.vue:69` 把 `tab` 写进 URL query。

**建议**：关键字模块、关键字、分页等关键筛选条件同步到 URL query。

---

### 2.2 主题切换、用户名、登出按钮只存在于首页

**影响**：切换到任何子页面后，切主题、查看用户信息、退出登录等入口即消失，用户被迫回到首页才能操作。

**证据**：`src/views/HomeView.vue:91–99` 的 `.top-right-actions` 是 HomeView 内 scoped fixed 定位。

**建议**：把顶栏（Logo / 全局菜单 / 用户头像下拉 / 主题切换）提到全局布局层。

---

### 2.3 部分页面缺少返回按钮，使用不一致

**影响**：用户在编辑器等二级页面找不到出口。

**证据**：经 grep 确认，以下页面缺少返回入口：

- `src/views/ManDocEditor.vue`（路径 `/operations/edit/:id?`，高频操作入口）；
- `src/views/PhonebookView.vue`。

其余 ServicesView、DevicesView、PrintersView、PhonesView、OperationsView、采购页、日志监控页、Admin 子页等 12 处已有 `BackButton` / `返回首页`。

**建议**：补全缺失页面的返回入口，或进一步用全局面包屑替代散落的 `BackButton`。

---

### 2.4 设备 U 高度校验失败静默，用户以为成功实际未写入

**影响**：用户点击"确定"后既没看到成功提示，也没看到报错，实际数据却未写入。

**证据**：`src/components/devices/DeviceForm.vue:69` 仅设置 `max`，而父组件 `onDeviceSubmit`（`src/views/DevicesView.vue:168–180`）在剩余 U 不足时静默查找其他位置，找不到则直接 `return`。

**建议**：提交前端做预校验，不满足时调用 `ElMessage.warning('机柜剩余 U 不足')` 明确反馈。

---

### 2.5 平板 / 窄屏下表格横向溢出

**影响**：平板或窄屏下出现横向滚动条，操作困难。

**证据**：`src/views/PhonesView.vue:30` 列表格列固定宽度合计超 700px、`src/views/procurement/ComputerProcurementTab.vue:30-56` 与 `PhoneProcurementTab.vue:34-60` 均为 10+ 列表格。仅 `PhonesView:329-332` 有 `@media (max-width: 640px)` 适配。

**建议**：表格容器加 `overflow-x: auto`，关键列 `fixed`，次要列允许隐藏。

---

### 2.6 批量删除后无撤销入口

**影响**：误删后无法恢复。

**证据**：`src/views/PhonebookView.vue:199-205`、`src/views/PrintersView.vue:260-268`、`src/views/procurement/ComputerProcurementTab.vue:427-437` 批量删除后仅 `ElMessage.success('已删除 N 条')`，无撤销入口。

**建议**：至少提供 5 秒内的"撤销"（前端暂存删除项并可在缓冲期内恢复）。

---

### 2.7 多处接口失败仅 `console.error`，用户无感知

**与 1.6 同理，扩展至**：`src/views/admin/AdminAtcomConfig.vue:33`、`src/views/procurement/ComputerProcurementTab.vue:502-504`、`src/views/procurement/PhoneProcurementTab.vue:489-491`。

---

### 2.8 话机缓存失效后列表全空，用户不知是宕机还是无数据

**影响**：运维人员以为所有话机"丢失"。

**证据**：`server/routes/phones.ts:340` 在 `/refresh` 失败时把 `cache` 置为 `null`，但 `phones.ts:363, 383, 416, 600` 等多个路由以 `cache?.data || []` 使用，导致缓存为空时直接返回空数组，前端无法区分"PBX 宕机"与"确实没有话机"。

**建议**：

- `cache = null` 这行移到 `discoverPhones()` **成功后**；
- 或在所有使用 `cache` 的入口做 `if (!cache) await ensurePhoneCache()`；
- 前端在 502 时 toast 明确的"PBX 连接失败"提示。

## 4. 用户可感知的安全与稳定性

以下问题在用户视角下可能遇到"莫名其妙"的报错或会话异常。

### 4.1 严重

**外源凭据硬编码 + 明文 HTTP**

`server/routes/phones.ts:50`、`:133`、`:194`、`:430`、`:549`、`:614` 写死 `admin/admin`，默认 Git 镜像 + 明文 HTTP，任何同网段用户都能嗅探 PBX 与话机密码。

**建议**：

- 生产部署强制 HTTPS；
- 启动时若 `system_config` 未配置凭据则拒绝启动，并在 admin 面板强制设置；
- `system_config` 查询接口对 `atcom_pbx_pass` 等字段脱敏返回 `••••`。

---

**JWT_SECRET 自动生成存 DB，重启后翻滚**

`server/middleware/auth.ts:21-31` 在 `jwt_secret` 不存在时自动生成并写入 DB。多实例部署、容器 / `pm2 restart` 重启会让所有用户瞬间掉线。

**建议**：`JWT_SECRET` 强制走 `process.env.JWT_SECRET`，未配置则 fail-fast（退出进程），DB 仅作 fallback 且只读。

---

**全局错误处理吞掉错误，但部分路由直接抛英文名词**

`server/index.ts:66-68` 全局捕获后仅返回"服务器内部错误"，但 `server/routes/admin.ts:202/226/247`、`phones.ts:468`、`operations.ts:500` 等仍显式返回英文 `err.message`（如 "FOREIGN KEY constraint failed"）。前端 `src/utils/http.ts:55`、`:62` 把 `err.message` 直接抛给上游 UI，无中文 fallback。

**建议**：

- 服务端统一 500 返回 `{ code: 500, message: '服务器内部错误', traceId }`，仅对 `SQLITE_CONSTRAINT_UNIQUE` / `SQLITE_CONSTRAINT_FOREIGNKEY` 翻译为中文；
- 前端 `http.ts` 兜底：当 `err.message` 匹配 `/SQLITE|HASH|constraint/i` 时替换为"操作失败，请稍后再试"。

---

**CORS 全开放 + 无 helmet**

`server/index.ts:25` 的 `app.use(cors())` 默认 `Access-Control-Allow-Origin: *`，配合无 `helmet` / CSP / `X-Frame-Options`，任何站点都能跨域调用带 Bearer 的敏感 API，并可嵌入 iframe 钓鱼。

**建议**：

- `app.use(cors({ origin: process.env.CORS_ORIGIN?.split(',') ?? 'http://localhost:5173', credentials: true }))`；
- 加 `helmet()` 中间件启用 CSP / HSTS / `X-Frame-Options` / `x-content-type-options`。

---

### 4.2 中等

**话机 / 机柜 / 分类等业务接口无字段校验**

`server/routes/printers.ts:75-88`、`devices.ts:21-50`、`operations.ts:127-146`、`admin.ts:179-204`（services 路由是唯一例外，见 `services.ts:96-107`）。用户输入超长字符串或错误类型直接触达 SQLite 报 500，前端只看到"服务器内部错误"。

**建议**：对 phones / printers / devices / admin CRUD 等路由补 zod / celebrate schema 校验，错误返回中文提示。

---

**列表接口全部无分页**

首页 dashboard 并发 8+ 单语句 COUNT（`server/routes/dashboard.ts:10-17, 285-304`），话机列表每行同步历史 IP 多次命中（`phones.ts:300-310`），`operation_logs` 接口全表回传。现场话机、日志稍多即明显卡顿。

**建议**：所有列表接口统一 `page / pageSize / total`，前端不再 `.map` 全量后再前段切片。

## 附录 A：严重度定义

- **严重（P0）**：阻断核心流程、导致数据损失、或存在安全漏洞；
- **中等（P1）**：明显影响效率或一致性，用户会反复受挫；
- **轻度（P2）**：细节打磨，影响专业感与可访问性。
